## Responsive design — components

Mobile/desktop split is Tailwind v4's `md:` (≥768px) — the only breakpoint used.

- **Tables vs cards**: every list page keeps a desktop `<table>`. Row components render two siblings: a `<tr className="md:hidden">` with `colSpan` wrapping a mobile card, and a `<tr className="hidden md:table-row">` with the original cells. The parent table is `table-auto md:table-fixed` so the colgroup pixel widths don't force horizontal overflow on mobile. See `src/components/TransactionRow.tsx` for the reference implementation. The desktop table column set is Date · Category · Store · Status · Amount · actions. The row carries **no inline Edit and no inline Verify** — editing was moved into the products/transaction modal (see below) and the only row action is **Delete** (confirm-twice). While a row's status is `processing` (a receipt scan is mid-flight) it **self-heals** via a `useRouter().refresh()` poll every 4 s — torn down the moment the status changes — so the row leaves `processing` even if the fire-and-forget scan's `revalidatePath` never reached this client. The whole row/card opens the modal instead (`title="View details"`). The `StatusBadge` (colour-coded `processing`/`unverified`/`ready_to_verify`/`verified`, falling back to `unverified` for unknown values) replaced the desktop Note column **and is itself the verify control**: when the status is `ready_to_verify` the pill renders as a `<button>` that calls `verifyTransaction` (with `e.stopPropagation()` so it doesn't also open the modal/expand the card); for every other status it's a plain `<span>`. On desktop the note is neither shown nor editable inline — it lives only in the mobile expanded card and the modal's edit form. `store` (optional merchant name) shows as its own desktop column (em-dash when null); editing it now happens in the modal. The mobile card shows the badge next to the date; because the badge can be an interactive button, the mobile collapsed header is a `div role="button"` (Enter/Space toggles expand) rather than a `<button>`, to avoid nested-button markup. Tap-to-expand reveals store + note + a "Details" button (opens the modal) + Delete. For pages where the note overflow isn't an issue (`/categories`, `/plan`, `/expenditures`) the rows stay tables and only the icon buttons get a 40px `inline-flex min-w-10 min-h-10` hit-area wrapper.
- **Primary action on mobile**: the inline create form on `/transactions` is `hidden md:block`. Mobile uses `src/components/TransactionCreateSheet.tsx` — a FAB anchored at `bottom-[calc(env(safe-area-inset-bottom,0px)+5rem)]` that opens a bottom sheet (`fixed inset-x-0 bottom-0 z-50 rounded-t-2xl`) reusing the same `createTransaction` server action via `useActionState`. The sheet auto-closes on successful submit by comparing `state.successCount` against a stored `lastSeenSuccess` in render (not in an effect — avoids `react-hooks/set-state-in-effect`). Sheet inputs use `text-base` to prevent iOS focus-zoom.
- **Receipt scanning on create**: both the desktop form and the mobile sheet embed the shared `ReceiptUpload` (`src/components/ReceiptUpload.tsx` — a nameless file input, so the image never rides along in the form's own submission; it downscales the photo to a JPEG data URL via canvas, falling back to `FileReader` under jsdom). When a receipt is staged the submit button reads "Scan & add" and a hidden `has_receipt` input makes `createTransaction` start the row `processing`. The shared `useReceiptScanCreate(state)` hook holds the staged image and, on the new `lastTxId`, fires `scanReceiptForTransaction` fire-and-forget (in an effect, guarded by a ref) so the row is added independently of the scan; it flips Processing → Ready to verify / Unverified live when the scan resolves.
- **Transaction / products modal**: `src/components/ProductsModal.tsx` is now the transaction detail+edit modal (still named `ProductsModal`). It's opened by clicking anywhere on a `TransactionRow` (`cursor-pointer`, `hover:bg-zinc-50`) on desktop, or the "Details" button in the mobile expanded card, with `e.stopPropagation()` on the Delete button / verify badge so they don't also open it. It takes `tx`, `categories`, and `onClose`. The modal renders via `createPortal(..., document.body)` to escape the `<tbody>` (a `<div>` can't be a `<tr>` sibling) — no SSR mount guard is needed because it only renders after a client click. Top of the body is `TransactionEditor`: a read-only details grid showing Amount and Date always, Category/Store/Note only when they have a value, and Type only when it's `income` (the default `spend` is hidden), with a pencil **Edit** toggle that swaps in a stacked form (amount/type/category-select/date/store/note — all fields editable) wired to `updateTransaction` (re-syncs from the current `tx` prop on entering edit, so a re-edit never shows a stale value). Below that, products are **hidden by default behind a "Show products (n)" toggle**; expanding reveals the `tx.products` list (live: `addProduct`/`updateProduct`/`deleteProduct` call `revalidatePath("/transactions")`, which refreshes the row's props while the modal stays open), inline per-item edit/delete (same confirm-twice delete pattern as the row) and an add form (both reuse a `ProductFieldsEditor`), plus the total line and `ReceiptScanner`. Each product item shows name (+ brand), `product_type`, and description on the left (tags are stored/editable but **not** rendered in the list), the line-item maths `price × quantity unit = cost` on the right — a bold **red dash** stands in for a missing `cost` — and the Edit/Delete icons anchored bottom-right. The add form is itself **collapsed behind an "Add product" button** — the field editor only appears after it's pressed, and collapses again on a successful add or Cancel. A non-blocking total line shows the product-cost sum: green `Total: <sum>` when it matches `tx.amount`, red `Total: <sum> (<tx.amount>)` when it doesn't (Reading A — divergence is allowed). `ReceiptScanner` (replacing the former `MockUpload` stub) uploads a receipt photo and attaches the AI-parsed line items as products, mirroring the create flow's **two-phase split**: pressing Scan awaits `startReceiptScan` (clears existing products — a scan *replaces* them — and marks the row `processing`); its `revalidatePath` re-flows the open modal's `tx`. Only once the row actually reads `processing` does an **effect** fire the background `scanReceiptForTransaction` (`src/actions/receipt.ts`) as a *separate* dispatch (staged image held in a `pendingImage` ref, a `fired` ref guards against double-firing and re-arms when `processing` clears). This separation matters: firing the vision scan in the *same* transition as `startReceiptScan` swallows that action's router refresh, so the cleared/processing state never reaches the UI and the row's status doesn't update until the whole scan finishes — exactly the create-flow reason the two dispatches are kept apart. The products list refreshes live off `revalidatePath("/transactions")` when the scan lands. While the transaction is `processing` the upload + Scan button are disabled (no re-scan mid-scan); a failed `startReceiptScan` shows inline. When the transaction has a stored receipt photo (`tx.receipt_id`, set once a scan has run), the scanner box shows a **"View receipt"** link opening `/api/receipts/[id]` in a new tab.
- **FilterPanel dropdown**: panel uses `w-[min(15rem,calc(100vw-2rem))] md:w-60` so it never spills past the right edge on narrow screens; the trigger summary truncates at `max-w-[10rem] md:max-w-[14rem]`.
- **Charts**: both chart containers use `h-72 md:h-[380px]`. The pie chart uses percentage radii (`innerRadius="37%"` / `outerRadius="63%"`) so it scales with the container while preserving the original 70/120px size at the desktop height.
