## Server actions

All DB writes live here. Each file is `"use server"` at the top, reads `FormData`, validates, calls `pool.query(...)`, and ends with `revalidatePath(...)` for every list page the mutation can affect.

### Two return shapes (pick by hook)

- **`TransactionFormState` / `CategoryFormState`** — `{ error?: string; successCount: number }`. Used with `useActionState` on create forms. `successCount` increments on success; the client compares the new count against a stored `lastSeenSuccess` to detect "a submit just succeeded" and trigger side effects (form reset, close the mobile sheet) without an effect.
- **`ActionResult`** — `{ ok: true } | { ok: false; error: string }`. Used with `useTransition` for row-level edit/delete and one-off mutations like `upsertPlan`. The client branches on `result.ok` after `startTransition`.

`ActionResult` is exported from `src/actions/transactions.ts` and imported by the other action files.

### Validation conventions

- Numbers via `Number(formData.get(...))`, then `!Number.isFinite(n) || n <= 0` for positive amounts/ids; `Number.isInteger(n) && 0 <= n <= 10` for `priority`. The transaction `amount` is **optional**: `parseOptionalAmount` in `transactions.ts` maps blank → `null` and otherwise applies the same positive-number rule.
- Strings: `((formData.get(k) as string | null) ?? "").trim()`; empty string → null for nullable fields like `note`.
- Whitelisted enums: `["income", "spend"].includes(type)` for transaction `type`.
- Date format: `DATE_RE = /^\d{4}-\d{2}-\d{2}$/` in `transactions.ts`, `MONTH_RE` for `YYYY-MM` is exported from `src/lib/filters.ts` and reused by `plans.ts`.
- Unique-violation handling: `INSERT` paths that can hit a `UNIQUE` constraint wrap the query in `try/catch` and check `err.code === "23505"` via the local `isUniqueViolation` helper, returning a friendly error instead of throwing.

### Plans use upsert

`upsertPlan` uses `INSERT … ON CONFLICT (category_id, month) DO UPDATE SET amount = EXCLUDED.amount`. One amount per `(category_id, month)` pair — see `src/db/migrations/` for the unique constraint.

### Categories are created on-the-fly from transactions

`createTransaction` accepts `category_name` (not `category_id`) and, when one is given, runs `INSERT … ON CONFLICT (user_id, name) DO UPDATE SET name = EXCLUDED.name RETURNING id` to either create or look up the category in a single round-trip. (The conflict target is `(user_id, name)` — the per-user unique constraint added in migration 006, not the original global `name` unique.) `updateTransaction` takes a `category_id` directly because the edit UI is a select against existing categories. Both amount and category are **optional** (migration 012), but not simultaneously blank with nothing else to fill them: `createTransaction` requires at least one of {amount, category, staged receipt (`has_receipt`)}, and `updateTransaction` with both blank checks the `receipts` table and rejects when no receipt is stored — both fail with "Add an amount, a category, or a receipt photo". A blank category means no upsert and no `/categories` revalidate.

### Transactions carry products

A transaction can have zero or more `products` line items (`src/actions/products.ts`). `createTransaction` inserts only the transaction row — it starts with **no products** (the user adds them later via the products modal). `transactions.amount` stays authoritative; product costs are an optional breakdown and aren't forced to sum to it. (Older rows backfilled with an `'other'` product by migration 007 may still exist; nothing depends on their presence.) `addProduct`/`updateProduct`/`deleteProduct` return `ActionResult`; `addProduct` validates transaction ownership via `userOwnsTransaction` (mirrors `userOwnsCategory`). Only `name` is required; `cost`, `price`, `amount` (quantity) and `discount` (money off that line — `cost` is the final paid figure with the discount already baked in, migration 013) are optional but must be positive when present (parsed via the shared `parsePositive` helper — blank → null); `unit` is an optional free-text string; `tags` come in as one comma-separated field and are split/trimmed into a `TEXT[]`. Each of the three calls `recomputeTransactionStatus(userId, transactionId)` afterward (update/delete recover the `transaction_id` via `RETURNING`), which re-derives `transactions.status`: `ready_to_verify` when the product costs sum to the **effective amount** — the manual `amount`, or the scanned `receipts.total` when no manual amount exists — within a loose `COST_TOLERANCE = 1`, else `unverified` — applied unconditionally, so a `verified` row can be downgraded. (Nothing is netted off either side: the scanned total is the final amount paid and per-product discounts are already baked into their costs.) A manual amount that disagrees with the scanned total (≥ `COST_TOLERANCE` apart) forces `unverified` no matter what the costs sum to, and with neither figure the row stays `unverified`. `recomputeTransactionStatus` and a bulk `insertProducts(userId, txId, fields[])` helper are **exported** from `products.ts` so the receipt-scan action reuses them (`addProduct` also routes its single insert through `insertProducts`).

### Receipt scanning

`scanReceiptForTransaction(formData)` in `src/actions/receipt.ts` (fields `transaction_id`, `image` = a `data:image/…` URL) attaches AI-parsed products to an existing transaction. It validates the id and `userOwnsTransaction`, calls `scanReceipt` (`src/lib/receipt-scan.ts` — one OpenAI vision call, json_schema structured output, zod-validated; takes the user's category names, rendered into the prompt **and** enforced as a response-schema enum, and returns `{ store, total, date, category, products }` — `total` being the receipt's printed grand total, always the **final amount paid** with every discount already reflected; per-item discounts ride on the products themselves with `cost` already discounted, and a check-wide discount is not extracted at all (the dormant `receipts.discount` column is unused — see `src/db/CLAUDE.md`)), stores the scanned grand total in `receipts.total` (never on `transactions.amount` — a manual amount stays authoritative), fills in transaction fields the user left blank — `category_id` (the scan answers with one of the user's category names or the literal `"other"`, lazily creating the per-user `other` category for the fallback), `store`, and `date` when it still equals today (i.e. the user kept the form default) — then bulk-inserts products via `insertProducts` and recomputes status. The recompute + `revalidatePath("/transactions")` run in a `finally`, so a failed scan returns `{ ok:false, error }` **and** still clears a `processing` row back to `unverified` (never stuck mid-scan). Used by the create flow (after `createTransaction` starts the row `processing` via the `has_receipt` flag and returns its new id as `lastTxId`) and by the products modal. The client downscales the photo and passes it to this action, which **stores it in the `receipts` table** (migration 011, one per transaction) via a private `saveReceiptImage` upsert *before* the vision call — so the photo survives a failed scan, and a re-scan replaces the stored image. A store failure is logged but never aborts the scan. The stored image is served by the authed route handler at `/api/receipts/[id]` and surfaced as `Transaction.receipt_id` (LEFT JOIN in `getTransactions`).

For the **modal re-scan**, the client first awaits `startReceiptScan(formData)` (same file): it deletes the transaction's existing products (a new scan *replaces* them) and marks the row `processing` via a guarded `UPDATE … WHERE status <> 'processing'` — a no-op update (already mid-scan) returns "A scan is already in progress", so a `processing` transaction can't be re-scanned. The modal then fires `scanReceiptForTransaction` fire-and-forget (mirroring the create flow), so the row shows `processing` immediately and the products land when the scan resolves.
