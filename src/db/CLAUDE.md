## Database

- Migrations run automatically on startup via `src/instrumentation.ts`, whose `register()` hook delegates to `migrate()` in `src/instrumentation-node.ts` (the actual runner — split out so the `fs`/`path`/`pg` imports stay off the edge runtime). Add numbered `.sql` files to `src/db/migrations/` (e.g. `010_add_col.sql`) — the runner applies any not yet recorded in the `_migrations` table, each in its own transaction. Never edit existing migration files.
- Fresh local DB: `createdb finmon`, set env vars in `.env`, then `npm run dev` — the instrumentation hook runs migrations on first request. There is no separate `db:init`; migrations are the only source of truth for schema.
- The runner sets `app.owner_*` GUCs (from `OWNER_USER_ID`/`OWNER_EMAIL`/`OWNER_NAME`/`OWNER_PASSWORD_HASH` env vars) on every migration's transaction. Migration `006_backfill_owner_and_lock.sql` reads them via `current_setting('app.owner_*', true)` to create the owner user + claim any orphan rows. **The four `OWNER_*` env vars must all be set or all unset** — partial config throws at startup. On a blank DB they can be omitted entirely; you then register normally through `/register`. On prod (or any DB with rows in `categories`/`plans`/`transactions` predating auth), they are required, otherwise migration 006's `SET NOT NULL` will reject the orphan rows and the deploy halts.
- `npm run db:seed:init` wipes the owner's three tables (`products` clears via the `transactions` cascade) and seeds a deterministic 3-month dataset (8 categories, transactions across the last 90 days, plans for the current and 2 prior months). Each transaction also gets a `store` (per-category merchant pool, ~10% null, income rows never get one), product line items, and an explicit `status`: ~15% of rows have no products and stay `unverified`; the rest get line items whose `cost`s sum **exactly** to `amount` and land `verified` (~45%) or `ready_to_verify`. Groceries split into 2–6 catalog items (brand/`product_type`/`unit`/occasional `tags`, ~75% with `price`+quantity); other categories get a single line item named from the note. `processing` is never seeded (it's transient, receipt-scan-only). Idempotent — re-running yields byte-identical data (generation flows entirely from the seeded `mulberry32` RNG). Requires `OWNER_USER_ID`.
- `npm run db:seed:month -- <1-12>` appends 0–5 transactions per day for the given month of the current year — with the same store/products/status decoration as `init` — owned by `OWNER_USER_ID`. Additive; re-running duplicates rows by design.
- `npm run db:hash-password '<password>'` prints a Better Auth password hash for use as `OWNER_PASSWORD_HASH`.
- DB env vars: `SQL_DB_HOST`, `SQL_DB_PORT`, `SQL_DB_NAME`, `SQL_DB_USER`, `SQL_DB_PASSWORD`. SSL is on by default (`rejectUnauthorized: false` — encrypts but does not verify the server cert, which suits a managed Postgres reached over TLS without a bundled CA). Set `SQL_DB_SSL=false` to disable TLS — which is what the prod compose deploy does (the app↔db link never leaves the private Docker network) and what local Postgres uses.
- Auth env vars: `BETTER_AUTH_SECRET` (`openssl rand -base64 32`), `BETTER_AUTH_URL` (full origin, e.g. `http://localhost:3000`).
- Email env vars: `RESEND_API_KEY` and `RESEND_FROM_EMAIL`. If `RESEND_API_KEY` is unset, verification/reset emails are logged to the server console (useful in dev).
- Receipt-scan env vars: `OPENAI_API_KEY` (required for receipt scanning) and optional `OPENAI_MODEL` (default `gpt-4o-mini`), read at call time in `src/lib/receipt-scan.ts`. If `OPENAI_API_KEY` is unset, the scan action returns a friendly error and the transaction settles on `unverified` — transactions otherwise work unchanged.
- Date columns are `TEXT` in ISO form: `transactions.date` = `YYYY-MM-DD`, `plans.month` = `YYYY-MM`. Filter by month with `LEFT(t.date, 7) = $month`.
- `plans.amount` (migration `014`): the `plans_amount_check` constraint was relaxed from `amount > 0` to `amount >= 0` so a plan of **0** ("budget nothing here") is storable. `upsertPlan` allows 0 (blank/negative still rejected). The plan page also treats a category with **no** plan row as 0, so spend against an unplanned category counts toward the month's total (surfaced as a negative "left") rather than vanishing — see `src/actions/CLAUDE.md`.
- `products` (migration `007`): line items making up a transaction — `transaction_id` (FK → `transactions`, cascade), `user_id`, `name` (the only mandatory field), plus optional `brand`, `cost` (`DOUBLE PRECISION`, `CHECK cost IS NULL OR cost > 0`), `product_type`, `tags` (`TEXT[]`, default `'{}'`), `description`. Migration `008` adds optional `price` / `amount` (quantity) / `unit` columns (`price`/`amount` are `DOUBLE PRECISION` with `> 0` CHECKs, `unit` is `TEXT`), independent of `cost` (no enforced `price * amount = cost`) — surfaced through the `Product` type, the add/update actions (positive-number validation, blank → null) and the products modal editor/display. Migration `013` adds an optional `discount` column (`DOUBLE PRECISION`, `> 0` CHECK) — the money taken off that line, informational: `cost` is always the final paid figure with the discount already subtracted, so nothing re-subtracts it. Cost lives on the line item, not a shared catalog, so the same type/brand can recur at different costs. `transactions.amount` stays authoritative — products are an optional breakdown, not forced to sum to it. Migration 007 backfilled one product named `'other'` (cost = amount) per pre-existing transaction, but that is the only place `'other'` defaults come from — `createTransaction` no longer creates a default product (new transactions start with none), and `db:seed` seeds realistic line items rather than `'other'` placeholders (see the `db:seed:init` bullet above). Those legacy `'other'` backfill rows are harmless and nothing depends on them. `getTransactions` attaches each row's `products` (one extra `transaction_id = ANY(...)` query, grouped in JS) so the transactions list / products modal need no further round-trip.
- `transactions.store` (migration `010`): optional `TEXT` merchant/store name, nullable (a transaction need not record where it happened). Validated like `note` in `transactions.ts` (trim, blank → null) on both create and update; surfaced through the `Transaction` type, the create form/sheet, and the transactions table (its own desktop column + the mobile expanded card and edit form). `getTransactions` returns it via `SELECT t.*`.
- `transactions.status` (migration `009`): `TEXT NOT NULL DEFAULT 'unverified'`, `CHECK (status IN ('processing', 'unverified', 'ready_to_verify', 'verified'))` — backfills every existing row with `'unverified'`. Recomputed in `src/actions/products.ts` (`recomputeTransactionStatus`) after each product add/update/delete (and after an amount edit): `ready_to_verify` when product costs sum to the **effective amount** — the manual `transactions.amount`, or `receipts.total` when there's no manual amount — within a loose `COST_TOLERANCE = 1` (`Math.abs(cost_total - effective) < 1`), else `unverified`. Two extra rules: a manual amount and a scanned `receipts.total` that disagree (≥ `COST_TOLERANCE` apart) force `unverified` regardless of the product costs, and with neither figure present there's nothing to match, so `unverified` too. `getTransactions` exposes status via `SELECT t.*`. `processing` is driven by receipt scanning: `createTransaction` starts a row as `processing` when a receipt is staged (`has_receipt` flag), and the scan action (`src/actions/receipt.ts`) recomputes it once the parsed products are attached (or on failure, clearing it back to `unverified`). `verified` is user-driven: clicking a `ready_to_verify` row's status tag calls `verifyTransaction` — which adopts `receipts.total` as the `amount` when no manual amount exists, so a verified row always has one.
- `receipts` (migration `011`): the uploaded receipt photo behind a scanned transaction — `transaction_id` (FK → `transactions`, cascade, **UNIQUE**: one receipt per transaction), `user_id`, `image BYTEA` (the client-downscaled ~100–300 KB JPEG), `content_type`, `created_at`. Written by `src/actions/receipt.ts` via upsert (`ON CONFLICT (transaction_id) DO UPDATE`) before the vision call, so a re-scan replaces the image and the photo survives a failed scan. Read by `getReceiptImage(userId, receiptId)` in `queries.ts` and streamed by the authed route handler `/api/receipts/[id]` (401 no session, 404 missing/foreign, `Cache-Control: private, no-store`). `getTransactions` LEFT JOINs it to expose `receipt_id` and `scanned_total` on each transaction (UNIQUE ⇒ no row multiplication). Migration `012` adds `total NUMERIC(12,2) CHECK (total > 0)` — the receipt's printed grand total as read by the scan: reset to `NULL` whenever a new image is stored (a new photo invalidates the old total), filled in after a successful scan, and never copied onto `transactions.amount` except by `verifyTransaction` (see the status bullet). Migration `013` also added `discount NUMERIC(12,2) CHECK (discount > 0)` — a check-wide discount as read by the scan — but that turned out wrong in practice: receipts print a **final** grand total with every discount already reflected, so netting a check-wide discount off the cost sum double-counted it. The column is now **dormant** (kept in the schema in case it's needed later, deliberately not dropped): nothing writes or reads it — the scan no longer extracts a check-wide discount, `total` is simply the final amount paid, and rows scanned on 0.5.0 may still hold stale values that are ignored. BYTEA-in-Postgres is deliberate: images ride along in DB backups/snapshots instead of needing a separate file-volume backup story.
- Optional `transactions.amount` / `transactions.category_id` (migration `012`): both columns dropped `NOT NULL` so a receipt scan can fill them in after creation. The app layer enforces "at least one of {amount, category, receipt}" on create and update (the receipt lives in another table, so a CHECK can't express it). Spend aggregations (`getPlansForMonth`, `getPlansSummary`, `getExpendituresByCategory`, `getExpenditureSeries`) count a scan-only transaction at `COALESCE(t.amount, r.total)` via a LEFT JOIN on `receipts`; `getTransactions` LEFT JOINs `categories` (a row may be uncategorized) and returns `r.total AS scanned_total`. **Uncategorized spend** (a spend transaction with `category_id IS NULL`) is kept in every aggregate under a shared sentinel `UNCATEGORIZED_ID = 0` / `UNCATEGORIZED_NAME = "Uncategorized"` (real ids are SERIAL ≥ 1) — these live in **`src/lib/categories.ts`**, not `queries.ts`, because `PlanRow` is a client component and a *value* import from `queries.ts` pulls `src/db/index.ts` (and `pg`) into the browser bundle, which fails the build at request time; type-only imports from `queries.ts` are erased and stay fine: `getExpendituresByCategory` and `getExpenditureSeries` `LEFT JOIN categories` + `COALESCE(c.id,0)/COALESCE(c.name,'Uncategorized')` (the series also `COALESCE(c.priority,-1)`, sorting it last) instead of an inner join that dropped it; the category-anchored `getPlansForMonth` / `getPlansSummary` can't reach category-less rows, so they append a synthetic non-editable "Uncategorized" row via the private `uncategorizedSpent(userId, months)` helper — only when `categoryIds == null` (no explicit filter, the only time it's in scope) and the spend is `> 0`. Its ordering is switchable via a `TransactionSort` arg (`"date"` default → `t.date DESC, t.id DESC`; `"added"` → `t.id DESC`, i.e. insertion order since `id` is SERIAL), driven by the `/transactions` `?sort=` param — see `src/lib/CLAUDE.md`.
- `bug_reports` (migration `015`): user-filed bug reports from the header's "Report a bug" button — `user_id` (FK → `"user"`, cascade), `email` (denormalized copy of the reporter's email so a report reads without joining Better Auth's `user` table), `message`, `created_at TIMESTAMPTZ DEFAULT now()`. Written by `submitBugReport` (`src/actions/bug-reports.ts`); nothing reads it in-app yet — reports are queried straight from the DB.
- Tenancy: every row in `categories` / `plans` / `transactions` / `products` / `receipts` / `bug_reports` has `user_id TEXT NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`. Reads in `src/db/queries.ts` take `userId: string` as their first arg; writes in `src/actions/*.ts` call `requireUser()` from `src/lib/dal.ts`. Better Auth's own tables (`user`, `session`, `account`, `verification`) use camelCase columns and quoted identifiers — added in migration `004_auth_tables.sql`.
