## Database

- Migrations run automatically on startup via `src/instrumentation.ts`, whose `register()` hook delegates to `migrate()` in `src/instrumentation-node.ts` (the actual runner — split out so the `fs`/`path`/`pg` imports stay off the edge runtime). Add numbered `.sql` files to `src/db/migrations/` (e.g. `010_add_col.sql`) — the runner applies any not yet recorded in the `_migrations` table, each in its own transaction. Never edit existing migration files.
- Fresh local DB: `createdb finmon`, set env vars in `.env`, then `npm run dev` — the instrumentation hook runs migrations on first request. There is no separate `db:init`; migrations are the only source of truth for schema.
- The runner sets `app.owner_*` GUCs (from `OWNER_USER_ID`/`OWNER_EMAIL`/`OWNER_NAME`/`OWNER_PASSWORD_HASH` env vars) on every migration's transaction. Migration `006_backfill_owner_and_lock.sql` reads them via `current_setting('app.owner_*', true)` to create the owner user + claim any orphan rows. **The four `OWNER_*` env vars must all be set or all unset** — partial config throws at startup. On a blank DB they can be omitted entirely; you then register normally through `/register`. On prod (or any DB with rows in `categories`/`plans`/`transactions` predating auth), they are required, otherwise migration 006's `SET NOT NULL` will reject the orphan rows and the deploy halts.
- `npm run db:seed:init` wipes the owner's three tables (`products` clears via the `transactions` cascade) and seeds a deterministic 3-month dataset (8 categories, transactions across the last 90 days, plans for the current and 2 prior months). Each transaction also gets a `store` (per-category merchant pool, ~10% null, income rows never get one), product line items, and an explicit `status`: ~15% of rows have no products and stay `unverified`; the rest get line items whose `cost`s sum **exactly** to `amount` and land `verified` (~45%) or `ready_to_verify`. Groceries split into 2–6 catalog items (brand/`product_type`/`unit`/occasional `tags`, ~75% with `price`+quantity); other categories get a single line item named from the note. `processing` is never seeded (it's transient, receipt-scan-only). Idempotent — re-running yields byte-identical data (generation flows entirely from the seeded `mulberry32` RNG). Requires `OWNER_USER_ID`.
- `npm run db:seed:month -- <1-12>` appends 0–5 transactions per day for the given month of the current year — with the same store/products/status decoration as `init` — owned by `OWNER_USER_ID`. Additive; re-running duplicates rows by design.
- `npm run db:hash-password '<password>'` prints a Better Auth password hash for use as `OWNER_PASSWORD_HASH`.
- DB env vars: `SQL_DB_HOST`, `SQL_DB_PORT`, `SQL_DB_NAME`, `SQL_DB_USER`, `SQL_DB_PASSWORD`. SSL is on by default (`rejectUnauthorized: false` — encrypts but does not verify the server cert, which suits a managed Postgres reached over TLS without a bundled CA). Set `SQL_DB_SSL=false` to disable TLS — which is what the prod compose deploy does (the app↔db link never leaves the private Docker network) and what local Postgres uses.
- Auth env vars: `BETTER_AUTH_SECRET` (`openssl rand -base64 32`), `BETTER_AUTH_URL` (full origin, e.g. `http://localhost:3000`).
- Email env vars: `RESEND_API_KEY` and `RESEND_FROM_EMAIL`. If `RESEND_API_KEY` is unset, verification/reset emails are logged to the server console (useful in dev).
- Receipt-scan env vars: `OPENAI_API_KEY` (required for receipt scanning) and optional `OPENAI_MODEL` (default `gpt-4o-mini`), read at call time in `src/lib/receipt-scan.ts`. If `OPENAI_API_KEY` is unset, the scan action returns a friendly error and the transaction settles on `unverified` — transactions otherwise work unchanged.
- Date columns are `TEXT` in ISO form: `transactions.date` = `YYYY-MM-DD`, `plans.month` = `YYYY-MM`. Filter by month with `LEFT(t.date, 7) = $month`.
- `products` (migration `007`): line items making up a transaction — `transaction_id` (FK → `transactions`, cascade), `user_id`, `name` (the only mandatory field), plus optional `brand`, `cost` (`DOUBLE PRECISION`, `CHECK cost IS NULL OR cost > 0`), `product_type`, `tags` (`TEXT[]`, default `'{}'`), `description`. Migration `008` adds optional `price` / `amount` (quantity) / `unit` columns (`price`/`amount` are `DOUBLE PRECISION` with `> 0` CHECKs, `unit` is `TEXT`), independent of `cost` (no enforced `price * amount = cost`) — surfaced through the `Product` type, the add/update actions (positive-number validation, blank → null) and the products modal editor/display. Cost lives on the line item, not a shared catalog, so the same type/brand can recur at different costs. `transactions.amount` stays authoritative — products are an optional breakdown, not forced to sum to it. Migration 007 backfilled one product named `'other'` (cost = amount) per pre-existing transaction, but that is the only place `'other'` defaults come from — `createTransaction` no longer creates a default product (new transactions start with none), and `db:seed` seeds realistic line items rather than `'other'` placeholders (see the `db:seed:init` bullet above). Those legacy `'other'` backfill rows are harmless and nothing depends on them. `getTransactions` attaches each row's `products` (one extra `transaction_id = ANY(...)` query, grouped in JS) so the transactions list / products modal need no further round-trip.
- `transactions.store` (migration `010`): optional `TEXT` merchant/store name, nullable (a transaction need not record where it happened). Validated like `note` in `transactions.ts` (trim, blank → null) on both create and update; surfaced through the `Transaction` type, the create form/sheet, and the transactions table (its own desktop column + the mobile expanded card and edit form). `getTransactions` returns it via `SELECT t.*`.
- `transactions.status` (migration `009`): `TEXT NOT NULL DEFAULT 'unverified'`, `CHECK (status IN ('processing', 'unverified', 'ready_to_verify', 'verified'))` — backfills every existing row with `'unverified'`. Recomputed in `src/actions/products.ts` (`recomputeTransactionStatus`) after each product add/update/delete: `ready_to_verify` when product costs sum to `transactions.amount` (within a loose `COST_TOLERANCE = 1`, i.e. `Math.abs(total - amount) < 1`), else `unverified`. `getTransactions` exposes it via `SELECT t.*`. `processing` is now driven by receipt scanning: `createTransaction` starts a row as `processing` when a receipt is staged (`has_receipt` flag), and the scan action (`src/actions/receipt.ts`) recomputes it once the parsed products are attached (or on failure, clearing it back to `unverified`). `verified` is user-driven: clicking a `ready_to_verify` row's status tag calls `verifyTransaction`.
- Tenancy: every row in `categories` / `plans` / `transactions` / `products` has `user_id TEXT NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`. Reads in `src/db/queries.ts` take `userId: string` as their first arg; writes in `src/actions/*.ts` call `requireUser()` from `src/lib/dal.ts`. Better Auth's own tables (`user`, `session`, `account`, `verification`) use camelCase columns and quoted identifiers — added in migration `004_auth_tables.sql`.
