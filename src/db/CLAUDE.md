## Database

- Migrations run automatically on startup via `src/instrumentation.ts`. Add numbered `.sql` files to `src/db/migrations/` (e.g. `007_add_col.sql`) — the runner applies any not yet recorded in the `_migrations` table, each in its own transaction. Never edit existing migration files.
- Fresh local DB: `createdb finmon`, set env vars in `.env`, then `npm run dev` — the instrumentation hook runs migrations on first request. There is no separate `db:init`; migrations are the only source of truth for schema.
- The runner sets `app.owner_*` GUCs (from `OWNER_USER_ID`/`OWNER_EMAIL`/`OWNER_NAME`/`OWNER_PASSWORD_HASH` env vars) on every migration's transaction. Migration `006_backfill_owner_and_lock.sql` reads them via `current_setting('app.owner_*', true)` to create the owner user + claim any orphan rows. **The four `OWNER_*` env vars must all be set or all unset** — partial config throws at startup. On a blank DB they can be omitted entirely; you then register normally through `/register`. On prod (or any DB with rows in `categories`/`plans`/`transactions` predating auth), they are required, otherwise migration 006's `SET NOT NULL` will reject the orphan rows and the deploy halts.
- `npm run db:seed:init` wipes the owner's three tables and seeds a deterministic 3-month dataset (8 categories, transactions across the last 90 days, plans for the current and 2 prior months). Idempotent — re-running yields byte-identical data. Requires `OWNER_USER_ID`.
- `npm run db:seed:month -- <1-12>` appends 0–5 transactions per day for the given month of the current year, owned by `OWNER_USER_ID`. Additive; re-running duplicates rows by design.
- `npm run db:hash-password '<password>'` prints a Better Auth password hash for use as `OWNER_PASSWORD_HASH`.
- DB env vars: `SQL_DB_HOST`, `SQL_DB_PORT`, `SQL_DB_NAME`, `SQL_DB_USER`, `SQL_DB_PASSWORD`. SSL is on by default (`rejectUnauthorized: false` — encrypts but does not verify the server cert, which is what RDS needs without a bundled CA). Set `SQL_DB_SSL=false` to disable TLS for local Postgres.
- Auth env vars: `BETTER_AUTH_SECRET` (`openssl rand -base64 32`), `BETTER_AUTH_URL` (full origin, e.g. `http://localhost:3000`).
- Email env vars: `RESEND_API_KEY` and `RESEND_FROM_EMAIL`. If `RESEND_API_KEY` is unset, verification/reset emails are logged to the server console (useful in dev).
- Date columns are `TEXT` in ISO form: `transactions.date` = `YYYY-MM-DD`, `plans.month` = `YYYY-MM`. Filter by month with `LEFT(t.date, 7) = $month`.
- `products` (migration `007`): line items making up a transaction — `transaction_id` (FK → `transactions`, cascade), `user_id`, `name` (the only mandatory field), plus optional `brand`, `cost` (`DOUBLE PRECISION`, `CHECK cost IS NULL OR cost > 0`), `product_type`, `tags` (`TEXT[]`, default `'{}'`), `description`. Cost lives on the line item, not a shared catalog, so the same type/brand can recur at different costs. `transactions.amount` stays authoritative — products are an optional breakdown, not forced to sum to it. Migration 007 backfills one product named `'other'` (cost = amount) per existing transaction; `createTransaction` applies the same default when none are specified, and `db:seed` backfills `'other'` products for seeded rows. `getTransactions` attaches each row's `products` (one extra `transaction_id = ANY(...)` query, grouped in JS) so the transactions list / products modal need no further round-trip.
- Tenancy: every row in `categories` / `plans` / `transactions` / `products` has `user_id TEXT NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`. Reads in `src/db/queries.ts` take `userId: string` as their first arg; writes in `src/actions/*.ts` call `requireUser()` from `src/lib/dal.ts`. Better Auth's own tables (`user`, `session`, `account`, `verification`) use camelCase columns and quoted identifiers — added in migration `004_auth_tables.sql`.
